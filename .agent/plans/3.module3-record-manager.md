# Module 3: Record Manager — Content Hashing & Deduplication

## Complexity: ✅ Simple — single-pass executable

## Context
Every upload blindly inserts new chunks. Upload the same PDF twice → double the chunks → retrieval returns duplicates → degraded quality. Module 3 fixes this by hashing file content on upload and checking for existing records before ingesting.

---

## What Changes

### 1. Database — Add `content_hash` column
Run in Supabase SQL Editor:
```sql
ALTER TABLE documents ADD COLUMN IF NOT EXISTS content_hash TEXT;
```

---

### 2. Backend — `app/routers/documents.py`
Read file bytes upfront, compute SHA-256 hash, apply dedup logic before any storage/DB writes.

Three cases after checking `SELECT * FROM documents WHERE user_id = ? AND filename = ?`:

| Case | Condition | Action |
|------|-----------|--------|
| New file | No existing record | Normal flow — upload to storage, insert doc, background ingest |
| Duplicate | Existing record, **same hash** | Return existing doc immediately — skip all storage/ingestion |
| Updated | Existing record, **different hash** | Delete old chunks → re-upload (upsert) → update doc record → background re-ingest |

Key logic:
```python
import hashlib

content = await file.read()
content_hash = hashlib.sha256(content).hexdigest()

existing = db.table("documents").select("*") \
    .eq("user_id", user_id).eq("filename", file.filename).execute()

if existing.data:
    doc = existing.data[0]
    if doc["content_hash"] == content_hash:
        return DocumentResponse(**doc)  # same content, skip
    else:
        # changed content — delete old chunks, re-ingest
        db.table("chunks").delete().eq("document_id", doc["id"]).execute()
        # upsert to storage, update doc record, background re-ingest
```

**Also:** Pass `content: bytes` directly to `ingest_document()` to avoid re-reading from storage.

### 5. Frontend — `frontend/src/hooks/useDocuments.ts`
`uploadFile` currently prepends every returned doc. If server returns existing doc (same-hash case), it would duplicate the list entry. Fix:
```typescript
setDocuments((prev) => {
  const exists = prev.some((d) => d.id === doc.id)
  return exists ? prev.map((d) => d.id === doc.id ? doc : d) : [doc, ...prev]
})
```

---

### 6. Frontend — Status Badge UI (`frontend/src/pages/DocumentsPage.tsx`)

The status badge must reflect all three outcomes clearly. Add two new statuses beyond the existing `pending / processing / ready / error`:

| Scenario | Status value | Badge label | Badge style |
|----------|-------------|-------------|-------------|
| First upload, processing | `processing` | Processing... | Yellow / animated |
| First upload, done | `ready` | Ready | Green |
| Re-upload, same content | `ready` | Already up to date | Green (no animation) |
| Re-upload, changed content, processing | `processing` | Updating... | Yellow / animated |
| Re-upload, changed content, done | `ready` | Updated | Green |
| Error | `error` | Error | Red |

**Implementation approach — use a response header flag instead of a new status column:**

The backend already returns the document object. To signal "same hash / already up to date" to the frontend without adding a new DB column, return a custom response header:

```python
# In documents.py — same-hash case
from fastapi.responses import JSONResponse
return JSONResponse(
    content=doc,
    headers={"X-Dedup-Result": "already-up-to-date"}
)
```

Frontend reads the header after upload and sets a local display label:
```typescript
const dedupResult = response.headers.get("X-Dedup-Result") // "already-up-to-date" | null
```

- If `"already-up-to-date"` → show **"Already up to date"** badge (green, no spinner)
- If `null` and doc was previously in the list → show **"Updated"** badge after status reaches `ready`
- If `null` and doc is new → normal **"Ready"** badge

Store the dedup label in local component state (not in the DB — it's a transient display hint that resets on page refresh, which is fine).
